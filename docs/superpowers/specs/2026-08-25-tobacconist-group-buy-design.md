# Tobacconist — система групповых закупок табака

## 1. Обзор и цель

Инструмент для организатора групповых закупок табака среди друзей в Telegram. Заменяет ручной процесс (гугл-таблица + переписка с барыгой) на бота с Mini App: сбор заказов участников, агрегация в единый заказ для барыги, учёт оплат и сверка поставки при получении.

Один администратор (организатор), закрытый круг участников (все, кто состоит в конкретном групповом чате Telegram, куда добавлен бот). Поддержка нескольких барыг (продавцов) с independent ценами и наличием.

## 2. Роли и доступ

- **Админ** — организатор, Telegram id зашит в конфиг (одна учётка на MVP). Управляет барыгами, ценами, наличием, раундами закупки, чек-листом сверки, отметками оплаты.
- **Участник** — любой пользователь, который **на момент запроса** состоит в сконфигурированном групповом Telegram-чате. Членство проверяется бэкендом через Bot API (`getChatMember`) на каждый чувствительный запрос/при открытии сессии мини-аппа — доступ не должен работать в обход группы просто по знанию ссылки на бота.
- Аутентификация в Mini App — через проверку подписи Telegram `initData` на бэкенде (bot token).

## 3. Модель данных

Глобальный справочник (не привязан к барыге):
- **Brand** — id, name
- **Flavor** — id, brandId, name
- **Weight** — фиксированный список: 100г, 250г (расширяемо в будущем без изменения архитектуры — отдельная таблица, не enum в коде)

Привязано к конкретному барыге:
- **Vendor** — id, name, archived: bool
- **VendorBrandPrice** — vendorId, brandId, pricePerKgEur (редактируется вручную админом; цена пачки = pricePerKgEur × weight/1000, не зависит от вкуса)
- **VendorFlavorAvailability** — vendorId, flavorId, weightId, available: bool, updatedAt, sourceUploadId (для отладки)

Раунд закупки:
- **PurchaseRound** — id, vendorId, status (`open`/`closed`), openedAt, closedAt, openedByUserId. При открытии раунда фиксируется снэпшот текущих `VendorBrandPrice` (в отдельную таблицу **RoundBrandPriceSnapshot**: roundId, brandId, pricePerKgEur) — расчёты внутри раунда всегда используют этот снэпшот, а не live-цену, чтобы поздние изменения цены не влияли на уже идущий раунд задним числом.
- **OrderItem** — id, roundId, userId, brandId, flavorId, weightId, quantity (int, штук пачек), createdAt, updatedAt. Доступны для добавления только позиции (flavor × weight), у которых `VendorFlavorAvailability.available = true` на момент раунда у выбранного барыги.
- **RoundPayment** — roundId, userId, paid: bool, markedAt, markedByUserId
- **DeliveryChecklistItem** — roundId, brandId, flavorId, weightId, expectedQty, receivedQty. Генерируется/пересчитывается при закрытии раунда (см. §6).

Пользователи:
- **User** — telegramId, displayName, role (`admin`/`member`), firstSeenAt

Загрузки для аудита:
- **AvailabilityUpload** — id, vendorId, brandId, weightId, imageRef, rawAiResponse (json), createdAt

## 4. Ассортимент и парсинг наличия (Gemini vision)

Цены вводятся вручную (форма в админ-панели мини-аппа): барыга → бренд → €/кг.

Наличие — через загрузку картинки:
1. Админ выбирает барыгу, бренд, граммовку (картинка обычно про одну такую комбинацию, например "DarkSide 250г")
2. Загружает фото "как есть" (в том числе с зачёркнутыми — недоступными — позициями)
3. Бэкенд отправляет картинку в Gemini vision с промптом на извлечение списка вкусов и признака "зачёркнуто" для каждого
4. Вкусы, которых ещё нет в справочнике для этого бренда, создаются автоматически
5. Результат показывается в мини-аппе как список вкусов с переключателем available/недоступен, предзаполненным по ответу ИИ — админ может поправить перед сохранением (зачёркивание не всегда идеально распознаётся)
6. При сохранении — **полностью заменяет** предыдущее состояние наличия для пары (бренд, граммовка) у этого барыги. Вкус, который был доступен раньше, но отсутствует в новой картинке, становится недоступным.

Если позиция становится недоступной уже после того, как кто-то её заказал в открытом раунде — существующая строка заказа **не удаляется автоматически**, а помечается в интерфейсе (у участника и у админа) как "больше не в наличии", решение остаётся за человеком.

## 5. Жизненный цикл раунда закупки

Только один активный (`open`) раунд одновременно во всей системе.

**Старт раунда** — двумя равнозначными способами:
- Из мини-аппа (админ-панель): кнопка "Начать раунд" → выбор барыги из списка
- Командой в чате `/start_round` → бот отвечает инлайн-кнопками со списком барыг → выбор

Оба создают `PurchaseRound(status=open)` + снэпшот цен, бот постит в группу объявление с `web_app`-кнопкой "🛍 Заказать".

**Пока раунд открыт:**
- Участник в мини-аппе видит ассортимент только выбранного барыги (бренды → доступные вкусы по каждой граммовке), формирует/редактирует свои строки заказа, видит свою сводку (кг, €) по зафиксированной цене раунда
- Админ видит живую агрегированную сводку по всем участникам
- Админ может снять слепок (см. §7) сколько угодно раз, не закрывая раунд

**Закрытие раунда:**
- Редактирование заказов участниками блокируется
- Генерируется/обновляется `DeliveryChecklistItem` из финальных агрегированных `OrderItem`

**Переоткрытие закрытого раунда** (если обнаружилась ошибка в сводке):
- Кнопка "Переоткрыть" в админ-панели → статус обратно `open`, участники снова могут редактировать
- При повторном закрытии: `expectedQty` в чек-листе пересчитывается по актуальным позициям, но уже введённый `receivedQty` для совпавших позиций (бренд+вкус+граммовка) **сохраняется** — прогресс сверки не теряется
- Отметки оплаты (`RoundPayment`) при переоткрытии/повторном закрытии не изменяются

## 6. Слепок заказа (снапшот для барыги)

Доступен в любой момент, пока раунд открыт (и после закрытия — для истории), без ограничения на количество раз. Два представления в мини-аппе:

- **Текст** — моноширинный блок, сгруппированный по бренду, построчно: `Бренд - Вкус - Граммовка - xКоличество` (например `DarkSide - CyberKiwi - 250g - x3`). Кнопка "Скопировать" через Telegram WebApp Clipboard API — для вставки барыге прямо в чат.
- **Таблица** — визуальное отображение в мини-аппе (Бренд / Вкус / Граммовка / Кол-во / Сумма). Кнопка "Выгрузить" — бэкенд генерирует XLSX/CSV и **отправляет его админу документом в личку через бота** (надёжнее скачивания файла из Telegram WebView, которое не везде стабильно работает).

## 7. Чек-лист сверки поставки

Доступен после первого закрытия раунда. Список позиций (бренд/вкус/граммовка), у каждой — "нужно N — привезли M" с кнопками `+`/`-` для M. Без жёсткого ограничения "M ≤ N" — барыга может привезти больше или меньше, система просто фиксирует факт.

## 8. Оплата

Простая бинарная отметка `paid` на пару (раунд, пользователь), выставляется только админом вручную в мини-аппе. Нет самостоятельного подтверждения оплаты участниками.

## 9. Расчёты на пользователя

Для каждого участника в рамках раунда: список позиций заказа, суммарный вес (кг), суммарная сумма (€, по цене раунда), статус оплаты.

## 10. История

Закрытые раунды сохраняются целиком (заказы, цены на момент раунда, чек-лист, оплаты) — доступны для чтения участнику (свои раунды) и админу (все раунды).

## 11. Технологии и деплой

- Монорепо (npm workspaces):
  - `/server` — Node.js/TypeScript, Fastify, grammY (бот), Drizzle ORM + SQLite, интеграция с Gemini vision API
  - `/mini-app` — React + Vite + TypeScript, Telegram WebApp SDK
  - `/shared` — общие TS-типы (DTO) между server и mini-app
- Бот работает в режиме **webhook** (не polling) — тот же публичный HTTPS-домен обслуживает и бота, и мини-апп
- Деплой на существующий VPS пользователя: **Traefik** как reverse-proxy + автоматический HTTPS; процесс — через PM2 или systemd
- SQLite-файл как БД, периодический бэкап копированием файла по cron
- Изображения для распознавания хранятся на диске сервера (или временно, если не нужна ретроспектива) — `AvailabilityUpload.imageRef` указывает на путь/файл

## 12. Граничные случаи

- Ошибка/таймаут распознавания Gemini — показываем ошибку в мини-аппе, разрешаем перезалить картинку, ничего не сохраняется до успешного парсинга
- Нельзя начать новый раунд, пока текущий открыт — интерфейс явно показывает, какой раунд активен
- Позиция стала недоступной после того, как её уже заказали — не удаляем строку заказа молча, помечаем "больше не в наличии" (см. §4)
- Один админ на MVP, список из нескольких админов — вне рамок текущей задачи

## 13. Тестирование

- Unit-тесты бизнес-логики: агрегация заказов по раунду, конвертация €/кг → цена пачки, генерация/пересчёт чек-листа сверки, сохранение `receivedQty` при переоткрытии раунда
- Интеграционный тест парсинга Gemini — с мок-ответом API (без реального вызова в CI)
- Ручное тестирование мини-аппа внутри самого Telegram (Telegram WebApp SDK плохо эмулируется вне него)

## 14. Вне рамок (явно исключено по итогам обсуждения)

- Свободный текстовый ввод заказа с ИИ-парсингом сообщений участников (только структурированный ввод через Mini App)
- Конвертация валют — все расчёты только в €
- Гибкие/произвольные граммовки — только фиксированный список (100г, 250г), расширяемый в коде/БД, не пользователем
- Несколько администраторов
- Автоматическая отправка заказа барыге (только копирование текста / пересылка файла себе в личку)
