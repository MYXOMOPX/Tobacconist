# Tobacconist — система групповых закупок табака

## 1. Обзор и цель

Инструмент для организатора групповых закупок табака среди друзей в Telegram. Заменяет ручной процесс (гугл-таблица + переписка с барыгой) на бота с Mini App: сбор заказов участников, агрегация в единый заказ для барыги, учёт оплат и сверка поставки при получении.

Один администратор (организатор), закрытый круг участников (все, кто состоит в конкретном групповом чате Telegram, куда добавлен бот). Поддержка нескольких барыг (продавцов) с independent ценами и наличием.

## 2. Роли и доступ

- **Админ** — организатор, Telegram id зашит в конфиг (одна учётка на MVP). Управляет барыгами, ценами, наличием, заказами (статусами, позициями), чек-листом сверки, отметками оплаты. **Админ при этом остаётся обычным участником**: он видит те же экраны и заказывает так же, как все, а управление — отдельная кнопка, в которую он заходит сознательно, а не режим, в котором он заперт.
- **Участник** — любой пользователь, который **на момент запроса** состоит в сконфигурированном групповом Telegram-чате. Членство проверяется бэкендом через Bot API (`getChatMember`) на каждый чувствительный запрос/при открытии сессии мини-аппа — доступ не должен работать в обход группы просто по знанию ссылки на бота.
- Аутентификация в Mini App — через проверку подписи Telegram `initData` на бэкенде (bot token).

## 3. Модель данных

Глобальный справочник (не привязан к барыге):
- **Brand** — id, name
- **Flavor** — id, brandId, name
- **Weight** — фиксированный список: 100г, 250г (расширяемо в будущем без изменения архитектуры — отдельная таблица, не enum в коде)

Привязано к конкретному барыге:
- **Vendor** — id, name, archived: bool
- **VendorBrandPrice** — vendorId, brandId, pricePerKgEur (редактируется вручную админом; цена пачки = pricePerKgEur × weight/1000, не зависит от вкуса)
- **VendorFlavorAvailability** — vendorId, flavorId, weightId, available: bool, updatedAt, sourceUploadId (для отладки)

Заказ:
- **Order** — id, vendorId, status (`ordering`/`awaiting_validation`/`done`/`rejected`), createdAt, statusChangedAt, createdByUserId. При создании заказа фиксируется снэпшот текущих `VendorBrandPrice` (в отдельную таблицу **OrderPriceSnapshot**: orderId, brandId, pricePerKgEur) — расчёты внутри заказа всегда используют этот снэпшот, а не live-цену, чтобы поздние изменения цены не влияли на уже идущий заказ задним числом.
- **OrderItem** — id, orderId, userId, brandId, flavorId, weightId, quantity (int, штук пачек — сколько заказано), deliveredQty (int, nullable — сколько фактически досталось этому участнику по итогам сверки; `null`, пока сверка не завершена), addedByUserId (кто фактически добавил строку — сам участник или админ), createdAt, updatedAt. Доступны для добавления только позиции (flavor × weight), у которых `VendorFlavorAvailability.available = true` на момент заказа у выбранного барыги.
- **OrderParticipant** — orderId, userId, ready: bool (участник сам отметил "я закончил выбирать", см. §5), readyAt, paid: bool, paidMarkedAt, paidMarkedByUserId. Одна строка на пару (заказ, участник), создаётся при первой активности участника в заказе.
- **DeliveryChecklistItem** — orderId, brandId, flavorId, weightId, expectedQty, receivedQty. Генерируется/пересчитывается при переходе в `awaiting_validation` (см. §7).

Пользователи:
- **User** — telegramId, displayName, role (`admin`/`member`), firstSeenAt

Загрузки для аудита:
- **AvailabilityUpload** — id, vendorId, brandId, weightId, imageRef, rawAiResponse (json), createdAt

## 4. Ассортимент и парсинг наличия (Gemini vision)

Цены вводятся вручную (форма в админ-панели мини-аппа): барыга → бренд → €/кг.

Наличие — через загрузку картинок. Единственное, что админ указывает руками, — барыга; всё остальное читается с самих скринов:

1. Админ выбирает барыгу и закидывает **любое количество скринов** прайса (в том числе с зачёркнутыми — недоступными — позициями)
2. Каждый скрин уходит в Gemini vision, который извлекает **бренд, граммовку и список вкусов** с признаком "зачёркнуто" для каждого. Бренд и граммовка возвращаются nullable: обрезанный скрин может не показывать ни того, ни другого
3. Распознанное имя бренда сопоставляется со справочником без учёта регистра, пробелов и пунктуации, с допуском на вхождение одного названия в другое ("DARKSIDE CORE" → `DarkSide`). Если уверенного совпадения нет — бренд считается нераспознанным, и его выбирает админ
4. Всё распознанное показывается на **экране сверки**: по карточке на скрин — бренд (выбор из справочника или создание нового), граммовка, список вкусов с переключателями. Админ правит что угодно перед сохранением; ошибка распознавания одного скрина не отменяет остальные
5. Скрины с одинаковой парой (бренд, граммовка) **объединяются** в одну карточку — длинный прайс часто не влезает в один скрин
6. Вкусы, которых ещё нет в справочнике для этого бренда, создаются при сохранении. Новый бренд создаётся только в момент сохранения, а не пока админ разбирается со скрином
7. При сохранении каждая пара (бренд, граммовка) из пачки **полностью заменяется**. Вкус, который был доступен раньше, но отсутствует в скринах этой пары, становится недоступным
8. Отдельный переключатель **"Убрать всё другое наличие"**: всё, что не попало в эту пачку скринов, становится недоступным у этого барыги — по всем брендам и граммовкам. Для случая "барыга прислал весь свой ассортимент целиком". Строки наличия при этом не удаляются, а переводятся в `available = false`, поэтому уже заказанные позиции не исчезают, а помечаются "больше не в наличии" (§12)

Модель Gemini задаётся переменной окружения `GEMINI_MODEL` (по умолчанию актуальная flash-модель): Google выводит идентификаторы моделей из обращения, и это не должно требовать релиза кода. Запросы к API повторяются при временных ошибках (503/429/таймаут) — под нагрузкой они возвращаются регулярно.

**Ручное заведение позиции** (страховка на случай, когда Gemini не справился или барыга назвал вкус словами): админ может добавить бренд и вкус руками — форма "бренд (выбор из существующих или новый) → название вкуса → граммовка → доступен". Создаёт `Flavor` (если такого ещё нет) и `VendorFlavorAvailability(available = true)` для выбранной пары (бренд, граммовка) у этого барыги, не затрагивая остальные вкусы. В отличие от загрузки фото, ручное добавление **не заменяет** состояние наличия целиком, а добавляет/правит одну позицию.

Если позиция становится недоступной уже после того, как кто-то её заказал в активном заказе — существующая строка заказа **не удаляется автоматически**, а помечается в интерфейсе (у участника и у админа) как "больше не в наличии", решение остаётся за человеком.

## 5. Жизненный цикл заказа

Заказ привязан к конкретному барыге. Одновременно допускается **несколько заказов у разных барыг**, но **не более одного активного (нетерминального: `ordering` или `awaiting_validation`) заказа на одну и ту же барыгу** — интерфейс не даёт создать второй заказ у барыги, пока первый не дошёл до `done`/`rejected`.

**Диаграмма статусов:**

```
ordering ⇄ awaiting_validation → done       (терминальный)
ordering  → rejected                        (терминальный)
awaiting_validation → rejected              (терминальный)
```

**Создание заказа** — двумя равнозначными способами:
- Из мини-аппа (админ-панель): кнопка "Начать заказ" → выбор барыги из списка (без активного заказа)
- Командой в чате `/start_order` → бот отвечает инлайн-кнопками со списком доступных барыг → выбор

Оба создают `Order(status=ordering)` + снэпшот цен (`OrderPriceSnapshot`). Бот постит в группу объявление с персональной `web_app`/deep-link кнопкой "🛍 Заказать", которая открывает Mini App сразу на экране именно этого заказа (`startapp=order_<id>`). Так как одновременно может существовать несколько таких объявлений (по числу активных заказов у разных барыг), в Mini App также есть отдельный экран-список "Активные заказы" (доступен через команду `/orders` или пункт меню), где участник видит все заказы в статусах `ordering`/`awaiting_validation`, сгруппированные по барыге, и выбирает нужный.

**Статус `ordering`:**
- Участник в мини-аппе видит ассортимент выбранного барыги (бренды → доступные вкусы по каждой граммовке), добавляет/редактирует/удаляет свои строки заказа, видит свою сводку (кг, €) по зафиксированной цене заказа
- Участник может отметить себя **готовым** ("я закончил выбирать", `OrderParticipant.ready = true`) и снять отметку обратно. Готовность — **только подсказка админу**, ничего не блокирует: с ready = true участник по-прежнему может править свои строки (при правке отметка автоматически сбрасывается в false), а админ может закрыть сбор, не дожидаясь готовности всех
- Админ видит живую агрегированную сводку по всем участникам и по каждому — готов он или ещё выбирает, может снять слепок (см. §6) сколько угодно раз
- Переходы: → `awaiting_validation` (кнопка "Сверка" — с подтверждением, что сбор закроется; сразу открывает экран сверки, см. §7), → `rejected` (кнопка "Отменить заказ")

**Статус `awaiting_validation`:**
- Участники больше не могут добавлять/редактировать/удалять свои строки заказа — только просмотр своей сводки (в т.ч. в общем списке активных заказов)
- Админ может добавить/изменить/удалить `OrderItem` за любого участника (например, докинуть забытую позицию) — такие строки помечаются `addedByUserId` админа
- Генерируется/обновляется `DeliveryChecklistItem` из агрегированных `OrderItem` на момент входа в этот статус
- Доступны кнопки: "Сверка" (открывает экран чек-листа, см. §7 — завершение заказа живёт там), "Вернуть в работу" (→ `ordering`), "Отменить заказ" (→ `rejected`)
- "Завершить заказ" (внизу экрана сверки) доступна **всегда**, а не только после заполнения чек-листа: если сверку не делали (или в ней всё сошлось), `deliveredQty` каждой строки проставляется равным `quantity` без всякого экрана распределения. Если в чек-листе есть расхождения — сначала обязателен экран распределения (см. §7.1)
- Переход в `ordering` и обратно в `awaiting_validation` можно повторять произвольное число раз

**Возврат `awaiting_validation` → `ordering`** (если обнаружилась ошибка в сводке):
- Участники снова могут редактировать свои строки заказа
- Отметки готовности (`OrderParticipant.ready`) сбрасываются в false — состав заказа снова меняется, старые подтверждения не актуальны
- При повторном переходе в `awaiting_validation`: `expectedQty` в чек-листе пересчитывается по актуальным позициям, но уже введённый `receivedQty` для совпавших позиций (бренд+вкус+граммовка) **сохраняется** — прогресс сверки не теряется
- Отметки оплаты (`OrderParticipant.paid`) при этих переходах не изменяются

**Статус `done`** — терминальный. Заказ полностью закрыт, переходов из него нет (нельзя вернуть в `ordering`/`awaiting_validation`). Доступен только для чтения — в истории (см. §10).

**Статус `rejected`** — терминальный. Ставится админом из `ordering` или `awaiting_validation` (отмена заказа целиком — например, барыга не смог/отказался). Чек-лист сверки не создаётся/не используется, `OrderItem` сохраняются как есть для истории. Заказ остаётся в списке истории с пометкой "отменён", без возможности возврата в работу.

## 6. Слепок заказа (снапшот для барыги)

Доступен в любой момент, пока заказ активен (и после `done`/`rejected` — для истории), без ограничения на количество раз. Два представления в мини-аппе:

- **Текст** — моноширинный блок, сгруппированный по бренду, построчно: `Бренд - Вкус - Граммовка - xКоличество` (например `DarkSide - CyberKiwi - 250g - x3`). Кнопка "Скопировать" через Telegram WebApp Clipboard API — для вставки барыге прямо в чат.
- **Таблица** — визуальное отображение в мини-аппе (Бренд / Вкус / Граммовка / Кол-во / Сумма), только на экране. Выгрузки файлом нет: барыге уходит скопированный текст.

## 7. Чек-лист сверки поставки

Отдельный экран, открывается кнопкой "Сверка". Доступен в статусе `awaiting_validation` (и на чтение — после `done`, для истории; в `rejected` не используется); из `ordering` та же кнопка сначала закрывает сбор. Каждое изменение сохраняется сразу — ушёл с экрана и вернулся, цифры на месте. Внизу — "Завершить заказ". Список позиций (бренд/вкус/граммовка), у каждой — "нужно N — привезли M" с кнопками `+`/`-` для M. Без жёсткого ограничения "M ≤ N" — барыга может привезти больше или меньше, система просто фиксирует факт.

## 7.1. Распределение расхождений по участникам

Чек-лист сводит расхождение к паре (бренд+вкус+граммовка), но платят конкретные люди — поэтому расхождение нужно превратить в `OrderItem.deliveredQty`. **Распределяет админ вручную**, автоматики нет: система не решает за него, кто из друзей останется без пачки.

- Экран открывается по кнопке "Завершить заказ" внизу сверки и показывает **только те позиции, где `receivedQty ≠ expectedQty`**. Всё, что сошлось, распределяется молча: `deliveredQty = quantity`
- По каждой расходящейся позиции — список участников, заказавших её, с заказанным количеством и степпером "досталось". Сверху счётчик со знаком и глаголом: "снять N", "раздать N" или "распределено"
- Кнопка "Завершить заказ" (→ `done`) активна, только когда по каждой расходящейся позиции сумма `deliveredQty` участников равна `receivedQty` — ни больше, ни меньше. Это касается и перевоза (M > N): лишние пачки тоже нужно кому-то приписать, иначе за них никто не заплатит
- Стартовое состояние — каждому проставлено ровно то, что он заказал: это не решение системы, а заготовка, в которой админ отмечает только разницу. При недовозе сумма заготовки больше привезённого и админ снимает лишнее, при перевозе — меньше, и админ раздаёт
- После перехода в `done` `deliveredQty` заморожен вместе с остальным заказом. Если ошиблись — только "Вернуть в работу" до перехода в `done`, из `done` возврата нет (§5)

## 8. Оплата

Простая бинарная отметка `paid` на пару (заказ, пользователь), выставляется только админом вручную в мини-аппе. Нет самостоятельного подтверждения оплаты участниками.

Сумма к оплате считается **по фактически доставшемуся количеству**: пока сверка не завершена — по `quantity`, после — по `deliveredQty`. У админа есть сводный экран оплат: список участников с суммой и переключателем "оплачено", сверху итог "оплачено X из Y участников, собрано A € из B €".

## 9. Расчёты на пользователя

Для каждого участника в рамках заказа: список позиций заказа (с пометкой, кто добавил — сам участник или админ), суммарный вес (кг), суммарная сумма (€, по цене заказа), статус готовности, статус оплаты. Если сверка завершена и по позиции есть расхождение — в строке показываются оба числа ("заказано 2 → досталось 1") и итог пересчитан по факту.

## 10. История

Заказы в статусах `done` и `rejected` сохраняются целиком (позиции, цены на момент заказа, чек-лист при наличии, оплаты) — доступны для чтения участнику (свои заказы) и админу (все заказы). `rejected`-заказы отмечены как отменённые.

Админ из истории заходит в управление закрытым заказом (кнопка "Управление") — тем же экраном, что и для активных. Переоткрыть заказ нельзя: кнопок переходов статуса в `done`/`rejected` нет, состав не меняется. **Отметки оплаты остаются доступны** — деньги за поставку ходят и после того, как заказ закрыт, и это единственное, что в завершённом заказе ещё меняется.

## 11. Интерфейс и дизайн-система

Макеты, сгенерированные в Google Stitch (`DesignTools/GoogleStitch.md`), используются **только как ориентир по компоновке**. Точные цвета, отступы и цифры берутся отсюда — в макетах они разъехались (две палитры, три вида таб-бара, ₽ вместо €, цены, не соответствующие €/кг).

**Токены** (единственный источник — `DesignTools/DESIGN.md`):
- Один акцент: `primary #F05E23`, нажатый `#C94A15`. Никакого второго "светлого primary" (`#FFB59C` из автопалитры Stitch) в интерфейсе нет
- Поверхности: фон `#121110`, карточка `#1C1B19`, приподнятая `#232120`, граница `#332F2B`. Тема **фиксированно тёмная**, не следует за темой телефона и за темой Telegram
- Статусы: `ordering` — зелёная заливка `#3DBD6C`, `awaiting_validation` — жёлтая заливка `#E8B923`, `done` — серый аутлайн `#8B857D`, `rejected` — красный аутлайн `#E5484D`. Правило: активные статусы заливкой, терминальные аутлайном
- Типографика: Inter для текста, JetBrains Mono с табличными цифрами (`tnum`) — для **всех** денег, весов и количеств. Шрифты подключаются локально, не из Google Fonts

**Формат данных в интерфейсе:**
- Валюта только € (§14), всегда два знака после запятой: `49.50 €`. Вес — в кг с двумя знаками: `1.25 кг`. Количество — целое, с префиксом `x`
- Цена пачки всегда выводится из `pricePerKgEur × граммовка / 1000` и не хранится отдельно: при 42 €/кг это 4.20 € за 100г и 10.50 € за 250г. Итог карточки обязан быть равен сумме её строк — расхождения в макетах Stitch не переносить
- Граммовки — только те, что есть в справочнике `Weight` (сейчас 100г и 250г). Никаких 125г из макетов
- Названия брендов пишутся как в справочнике (`DarkSide`, `MustHave`, `BlackBurn`), интерфейс их не приводит к своему регистру
- Весь интерфейс на русском. Английских подписей быть не должно нигде, включая админские экраны

**Интеграция с Telegram:**
- Шапку с кнопкой "назад" рисует Telegram (`BackButton`) — свои шапки со стрелкой не дублируем; заголовок экрана, если нужен, идёт отдельной строкой в контенте
- Главное действие экрана — нативный `MainButton`; собственные sticky-панели внизу оставляем только там, где рядом с кнопкой нужна сводка (панель "Твой заказ: N позиций, X кг, Y €")
- Учитывать safe area снизу и вертикальные вставки Telegram; вьюпорт 375–430px
- Копирование слепка — через `WebApp.clipboard`, выгрузка файла — документом в личку от бота (§6), а не скачиванием из WebView

**Навигация:** нижний таб-бар, единый на всех экранах, где он есть. Участник — 2 вкладки: "Заказы", "История". Админ — 3: "Заказы", "Барыги", "История". Модальные потоки (чек-лист, распределение расхождений, bottom-sheet'ы) открываются поверх, без таб-бара.

**Состояния.** Для каждого экрана со списком обязательны четыре состояния, а не только "данные есть": загрузка (skeleton в форме будущих карточек), пусто (нет активных заказов / пустая история / у барыги нет цен или наличия), ошибка (сеть, 403 "ты не в группе", таймаут Gemini) с кнопкой "Повторить", данные. Деструктивные действия ("Отменить заказ", замена наличия по фото) требуют подтверждения.

**Карта экранов** (участник / админ):
1. Активные заказы — список по барыгам со статус-бейджем и своей сводкой; у админа дополнительно кнопка управления и FAB "новый заказ"
2. Ассортимент заказа, `ordering` — бренды → вкусы → граммовки, степперы, поиск по вкусу, sticky-сводка; позиция, ставшая недоступной, помечена "больше не в наличии"
3. Ассортимент заказа, `awaiting_validation` — то же, но read-only: степперы скрыты, сверху баннер "Добавление позиций закрыто, идёт сверка"
4. Мой заказ — свои позиции, вес, сумма, готовность, статус оплаты, пометки "добавлено администратором" и результат сверки
5. Новый заказ (админ) — bottom-sheet выбора барыги; барыги с активным заказом заблокированы с подписью "уже есть активный заказ" и бейджем текущего статуса
6. Управление заказом (админ) — агрегированная корзина, участники с готовностью/суммой, слепок с кнопкой "Скопировать текст", таблица слепка, кнопки переходов статуса
7. Корзина участника (админ) — открывается тапом по участнику на экране управления. Отметка оплаты (работает в любом статусе, в т.ч. после `done` — §10), итоги, и весь ассортимент барыги со степперами, где у позиций участника проставлены его количества. Правка доступна в `ordering` и `awaiting_validation`. Позиции, вылетевшие из наличия, показаны отдельной карточкой сверху — иначе их не видно, а на сумму они влияют (§12)
8. Чек-лист сверки — "нужно N / привезли M" со степперами и прогрессом
9. Распределение расхождений (§7.1) — только расходящиеся позиции, степперы по участникам, счётчик распределённого
10. Оплаты (админ) — сводка "оплачено X из Y, собрано A € из B €" и список участников с переключателями
11. Барыги (админ) — только список барыг и общий справочник брендов; всё про конкретного барыгу — на его странице
11a. Страница барыги (админ) — переименование, цены по брендам, текущее наличие по парам (бренд, граммовка) с переключателем на каждый вкус, ручное добавление позиции, загрузка скринов, удаление барыги с подтверждением. Барыгу, у которого уже были заказы, удалить нельзя — он уходит в архив, иначе история заказов перестанет читаться (§10)
12. Распознавание фото — какой барыга/бренд/граммовка обрабатывается, прогресс, список вкусов с переключателями, ошибка с возможностью перезалить
13. История — завершённые и отменённые заказы; тап открывает read-only детали заказа с чек-листом и оплатами. У админа на каждом заказе кнопка "Управление" — экран 6 без переходов статуса, но с отметками оплаты (§10)

## 12. Технологии и деплой

- Монорепо (npm workspaces):
  - `/server` — Node.js/TypeScript, Fastify, grammY (бот), Drizzle ORM + SQLite, интеграция с Gemini vision API
  - `/mini-app` — React + Vite + TypeScript, Telegram WebApp SDK
  - `/shared` — общие TS-типы (DTO) между server и mini-app
- Бот работает в режиме **webhook** (не polling) — тот же публичный HTTPS-домен обслуживает и бота, и мини-апп
- Деплой на существующий VPS пользователя: **Traefik** как reverse-proxy + автоматический HTTPS; процесс — через PM2 или systemd
- SQLite-файл как БД, периодический бэкап копированием файла по cron
- Изображения для распознавания хранятся на диске сервера (или временно, если не нужна ретроспектива) — `AvailabilityUpload.imageRef` указывает на путь/файл

## 13. Граничные случаи

- Ошибка/таймаут распознавания Gemini — показываем ошибку в мини-аппе, разрешаем перезалить картинку, ничего не сохраняется до успешного парсинга
- Нельзя начать новый заказ у барыги, пока у неё уже есть активный (`ordering`/`awaiting_validation`) заказ — интерфейс явно показывает, какие заказы активны и у каких барыг
- Позиция стала недоступной после того, как её уже заказали — не удаляем строку заказа молча, помечаем "больше не в наличии" (см. §4)
- Один админ на MVP, список из нескольких админов — вне рамок текущей задачи
- Заказ в `rejected` не участвует в проверке "один активный заказ на барыгу" — после отмены у барыги сразу можно открыть новый заказ
- Барыга привёз **больше** заказанного — распределяется так же, как недовоз (§7.1): лишнее нужно кому-то приписать, иначе сумма к оплате не сойдётся с реально полученным
- Позицию заказал один участник, а привезли 0 — `deliveredQty = 0`, строка остаётся в заказе для истории и не попадает в сумму к оплате
- Участник отметился готовым, а потом поправил свои позиции — готовность автоматически сбрасывается
- Участник вышел из группового чата после того, как заказал — его строки остаются в заказе (админ уже закупился), но доступ к мини-аппу он теряет по §2

## 14. Тестирование

- Unit-тесты бизнес-логики: агрегация заказов, конвертация €/кг → цена пачки, генерация/пересчёт чек-листа сверки, сохранение `receivedQty` при возврате `awaiting_validation` → `ordering` → `awaiting_validation`, проверка ограничения "один активный заказ на барыгу", переходы статусов (включая запрет переходов из `done`)
- Unit-тесты сверки и денег: распределение расхождений (§7.1) — заготовка "пропорционально заказанному", запрет завершить заказ при нераспределённом остатке, случай перевоза; проставление `deliveredQty = quantity` при завершении без расхождений; пересчёт суммы к оплате по `deliveredQty`
- Unit-тесты готовности: сброс `ready` при правке своих позиций и при возврате заказа в `ordering`
- Интеграционный тест парсинга Gemini — с мок-ответом API (без реального вызова в CI)
- Ручное тестирование мини-аппа внутри самого Telegram (Telegram WebApp SDK плохо эмулируется вне него)

## 15. Вне рамок (явно исключено по итогам обсуждения)

- Свободный текстовый ввод заказа с ИИ-парсингом сообщений участников (только структурированный ввод через Mini App)
- Конвертация валют — все расчёты только в €
- Гибкие/произвольные граммовки — только фиксированный список (100г, 250г), расширяемый в коде/БД, не пользователем
- Несколько администраторов
- Автоматическая отправка заказа барыге (только копирование текста / пересылка файла себе в личку)
- Дедлайн сбора заказов (Stitch нарисовал "до пт, 19:00") — сбор закрывает админ руками, автозакрытия по времени нет
- Автоматическое распределение недовоза между участниками — только вручную админом (§7.1)
- Частичная оплата и суммы платежей — отметка `paid` бинарная (§8)
