# Дизайн Mini App через OpenDesign (open-design.ai)

OpenDesign — открытый (Apache-2.0) **десктопный** инструмент, который
работает не сам по себе, а как оболочка над кодирующим AI-агентом
(Claude Code, Codex, Cursor, Gemini CLI и т.д.) — подключает его к
проекту и заставляет генерировать UI, следуя единой дизайн-системе.
Отличие от Claude Artifacts и Google Stitch: результат — не
одноразовая картинка/мокап, а **настоящие файлы**, которые ложатся на
диск в песочнице с живым предпросмотром, и их можно экспортировать.

Источник требований — актуальная спека:
`docs/superpowers/specs/2026-08-25-tobacconist-group-buy-design.md`.

> Я собрал этот файл по публичному описанию инструмента (сайт
> open-design.ai), а не по скриншотам реального интерфейса — если
> шаги/названия кнопок на экране будут отличаться, кинь скриншот, я
> поправлю файл под фактический UI (как сделал с Stitch).

## Важно: держи вывод отдельно от реального кода приложения

OpenDesign генерирует не мокап, а рабочие файлы прямо в файловую
систему. На этом этапе нам нужен именно дизайн для согласования, а не
преждевременная реализация фронта. Поэтому:

- Указывай OpenDesign работать в отдельной **пустой** папке-песочнице
  (например `DesignTools/opendesign-output/`, не коммить её содержимое
  без надобности), а **не** в `mini-app/` или `server/` — реальный
  фронт мы делаем отдельно, после утверждения дизайна, своими руками.
- Относись к сгенерированным файлам как к референсу (вёрстка, цвета,
  компоновка), а не как к финальному коду продакшена.

## Готовый DESIGN.md

В этой же папке лежит `DesignTools/DESIGN.md` — уже заполненный по
формату спецификации Google Labs (`google-labs-code/design.md`),
который понимает как OpenDesign, так и Google Stitch. Он описывает:
фиксированную тёмную тему (угольно-чёрный фон, приподнятые поверхности
без теней), акцентный цвет `#F05E23` ("ember"-стилистика), палитру
статусов заказа (`ordering`/`awaiting_validation`/`done`/`rejected` —
заливка для активных, аутлайн для терминальных), моноширинный регистр
для всех денег/веса/количеств, отступы, скругления, таб-бар,
bottom-sheet и стиль базовых компонентов (кнопки, карточки, бейджи,
степпер). Не переписывай его заново под OpenDesign — просто укажи
инструменту загрузить этот файл как основу бренда перед первой
генерацией. Рядом лежит `DesignTools/sample-data.json` — демо-данные
(барыги, бренды, вкусы, участники, примеры заказов на все 4 статуса) —
тот же файл используют промпты для Claude и Stitch; загрузи его через
блок "Загрузить код, изображения, шрифты и логотипы" (или его аналог
в OpenDesign) вместе с `DESIGN.md`, чтобы экраны использовали одни и
те же имена и цифры, а не выдуманные заново.

## Флоу в OpenDesign (по шагам)

1. **Подключи агента.** OpenDesign сам не генерирует — ему нужен
   рабочий AI-агент. Раз мы уже работаем в Claude Code — подключи
   именно его (в настройках/конфиге OpenDesign выбери Claude Code как
   backend-агента), не нужно заводить отдельно Cursor/Codex ради этого.
2. **Загрузи `DESIGN.md`.** На старте проекта — экран установки
   "визуального направления" (палитра/типографика/отступы) — вместо
   того чтобы настраивать всё заново вручную, подключи готовый файл
   `DesignTools/DESIGN.md` из этого репозитория как источник бренда.
3. **Опиши цель одной строкой** (это первый шаг флоу — "опишите цель
   одной строкой или выберите шаблон") — используй промпты по экранам
   ниже, по одному экрану за раз.
4. **Проверь предпросмотр** в песочнице после каждой генерации — раз
   это реальные файлы, легче поймать нестыковки со статусной моделью
   (например, что кнопка "Отменить" не покрашена в акцентный оранжевый)
   сразу, чем потом на этапе фронта.
5. **Экспортируй** только то, что действительно устраивает — в
   папку-песочницу, не в реальный `mini-app/`.

## Промпты по экранам (одна строка на экран)

Вставляй по одному, каждый — отдельный запуск генерации.

1. **Список активных заказов** — "Экран списка активных заказов для
   участника: карточки заказов по продавцам со статус-бейджем, числом
   позиций пользователя и суммой в евро, пустое состояние если заказов
   нет."
2. **Экран заказа, статус "Сбор заказов"** — "Детальный экран одного
   заказа в статусе 'Сбор заказов': ассортимент по брендам и вкусам,
   переключатели граммовки, степпер количества на каждую позицию,
   внизу прилипающая панель со сводкой 'Мой заказ' и суммой."
3. **Экран заказа, статус "На сверке"** — "Тот же экран заказа, но
   статус 'На сверке': баннер о том, что добавление позиций закрыто,
   список своих позиций без возможности редактирования, одна строка
   помечена как добавленная администратором."
4. **Своя сводка по заказу** — "Экран 'Мой заказ': список своих
   позиций, итоговый вес и сумма, бейдж статуса оплаты (оплачено/не
   оплачено), статус-бейдж заказа внизу."
5. **История заказов** — "Экран истории заказов участника: те же
   карточки заказов, что в списке активных, но только со статусами
   'Завершён' и 'Отменён', без действия добавить, только просмотр."
6. **Админ — старт заказа** — "Экран выбора продавца для нового
   заказа (админ): список продавцов с кнопкой 'Начать заказ', у
   продавца с уже активным заказом кнопка неактивна и вместо неё
   статус-бейдж текущего заказа."
7. **Админ — сводка заказа и статусы** — "Сводный экран заказа для
   админа: позиции агрегированы по всем участникам, статус-бейдж 'На
   сверке', ряд кнопок 'Завершить заказ' (основная), 'Вернуть в
   работу', 'Чек-лист сверки' (вторичные), 'Отменить заказ'
   (деструктивная), блок слепка для продавца с кнопками 'Скопировать'
   и 'Выгрузить'."
8. **Админ — добавить позицию участнику** — "Модальное окно 'Добавить
   позицию участнику' (доступно только в статусе 'На сверке'): выбор
   участника, затем бренд/вкус/граммовка/количество, кнопка
   'Добавить'."
9. **Чек-лист сверки поставки** — "Экран сверки поставки: прогресс
   'сверено X из Y позиций' вверху, список позиций с 'нужно N' и
   степпером 'привезли M'."
10. **Оплата участников** — "Экран оплаты для админа: сводка 'оплачено
    X из Y участников, собрано Z € из W €', список участников с суммой
    и переключателем оплачено/не оплачено."

## Ограничения, которые нужно держать в голове

- Это самый "тяжёлый" из трёх инструментов (десктоп-приложение +
  подключение агента с собственным API-ключом/биллингом агента,
  BYOK — счёт идёт от использования подключённого агента, не от
  самого OpenDesign).
- Раз агент реально пишет файлы — просмотри сгенерированный код так же,
  как обычный AI-generated код, прежде чем на что-то опираться: он
  может использовать библиотеки/паттерны, которые не совпадают с нашим
  реальным стеком (React + Vite, см. §11 спеки) — это ожидаемо, задача
  этапа дизайна не в этом.
- Если после нескольких экранов стиль расходится с `DESIGN.md`, явно
  попроси агента "сверься с DESIGN.md и приведи компонент к нему" —
  инструмент держит файл в памяти агента, но точечная сверка не лишняя.
