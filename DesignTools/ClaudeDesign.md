# Дизайн Mini App через Claude (Artifacts)

Цель этого файла — дать промпты, с которыми можно прийти в обычный чат Claude.ai
(модель с доступом к Artifacts, например Claude Opus/Sonnet) и получить
интерактивные HTML/CSS-макеты экранов Mini App, ещё до того как мы пишем
реальный React-фронт. Источник требований — актуальная спека:
`docs/superpowers/specs/2026-08-25-tobacconist-group-buy-design.md`.
Цвета/типографика/отступы ниже продублированы из `DesignTools/DESIGN.md`
(тот же файл используют промпты для Stitch и OpenDesign) — если токены
там поменяются, синхронизируй и этот файл. Демо-данные (барыги, бренды,
вкусы, участники, примеры заказов на все статусы) — в
`DesignTools/sample-data.json`, тот же набор используют промпты для
Stitch и OpenDesign; можешь вставить содержимое файла в чат Claude
вторым сообщением, чтобы макеты использовали одни и те же имена и
цифры.

## Как пользоваться этим файлом

1. Открой новый чат в Claude.ai, включи Artifacts (по умолчанию включены).
2. Первым сообщением вставь блок **"Системный контекст"** целиком — он один
   на весь диалог, дальше не повторяется.
3. Дальше по одному вставляй промпты из **"Промпты по экранам"** — каждый
   экран отдельным сообщением, чтобы Claude успевал сфокусироваться и не
   смешивал разметку разных экранов в одном артефакте.
4. Проси варианты и правки в том же диалоге ("сделай карточки крупнее",
   "перенеси статус-бейдж наверх") — Claude обновляет тот же artifact.
5. Держи один артефакт = один экран. Так проще сравнивать и сохранять то,
   что понравилось, не теряя остальное.

## Системный контекст (вставить первым сообщением)

```
Ты помогаешь спроектировать визуальный дизайн Telegram Mini App —
приложения для групповых закупок табака среди друзей. Организатор
(админ) открывает заказ у конкретного продавца ("барыги"), участники
закрытой группы Telegram добавляют себе позиции (бренд → вкус →
граммовка → количество), дальше идёт сверка поставки и отметки оплаты.

Технические рамки, которые ОБЯЗАТЕЛЬНО учитывать в макете:
- Это Telegram Mini App: экран открывается внутри Telegram (WebView) на
  телефоне. Ширина вьюпорта ~360–430px, высота — весь экран телефона
  минус системный header Telegram. Верхний системный header (с названием
  чата/бота, кнопкой "назад") рисует сам Telegram — его в макете
  дублировать не нужно, но нужно оставлять под него отступ сверху.
- Telegram Mini App поддерживает нативную "MainButton" — широкую кнопку,
  прилипшую к низу экрана (высота ~50px, на весь ширину минус отступы).
  Главное действие экрана (например "Добавить в заказ", "Сохранить")
  должно быть либо этой кнопкой, либо стилизовано под неё.
- Фиксированная тёмная тема — приложение НЕ подстраивается под
  светлую/тёмную тему Telegram, у него всегда одна и та же тёмная
  тема (угольно-чёрный фон, светлее — карточки, ещё светлее —
  приподнятые элементы вроде bottom-sheet). Светлый вариант делать не
  нужно вообще.
- Мобильный, тач-first интерфейс: минимальная кликабельная область 44px,
  крупные степперы количества (+/-), не мелкие иконки-ссылки.
- Внизу экрана — постоянный таб-бар с текстовыми вкладками без иконок
  (у участника: "Заказы", "История"; у админа ещё "Барыги" и текущий
  раздел управления заказом), активная вкладка подчёркнута акцентным
  цветом снизу. Модальные потоки (например выбор барыги при старте
  нового заказа) — не отдельная страница, а bottom-sheet, выезжающий
  снизу поверх таб-бара.
- Все денежные суммы, вес (кг) и количества набирай **моноширинным
  шрифтом** (например JetBrains Mono, табличные цифры) — это
  отличает их от обычного текста названий/подписей и делает похожим
  на показания приборной панели, а не на обычный текст.
- Два разных пользователя интерфейса: обычный участник (member) и
  админ. У админа те же экраны + дополнительные админские действия и
  кнопки статусов — не отдельное приложение, а расширенный режим тех же
  экранов.

Фирменный акцентный цвет: `#F05E23` (тёплый оранжевый, "ember"-стилистика
— тлеющие угли на угольно-чёрном фоне). Это ЕДИНЫЙ акцент бренда:
используй его для основных кнопок/MainButton, активной вкладки
таб-бара, крупных положительных сумм и т.п. — везде, где нужен один
узнаваемый цвет действия. Не путай его со статус-бейджами ниже — это
разные, самостоятельные палитры, статусные цвета не должны совпадать с
`#F05E23`, чтобы бейдж статуса и обычная кнопка-действие не сливались
визуально.

Статусная модель заказа (Order.status), она должна быть визуально
считываемой с первого взгляда через цветной бейдж/чип (палитра статусов
своя, отдельная от акцента `#F05E23` — см. выше). У бейджа статуса два
визуальных варианта: **заливка** — для активных/актуальных статусов
(это ещё в работе прямо сейчас), **аутлайн** (только цветная обводка и
текст, без заливки) — для терминальных/архивных статусов (это уже
прошлое):
- `ordering` — "Сбор заказов" — можно добавлять позиции. Зелёный,
  заливка.
- `awaiting_validation` — "На сверке" — участники больше не добавляют
  позиции (только смотрят свою сводку), админ донабирает/сверяет.
  Жёлтый (не оранжевый — чтобы не путался с акцентным `#F05E23`),
  заливка.
- `done` — "Завершён" — терминальный статус, только история, серый,
  аутлайн.
- `rejected` — "Отменён" — терминальный статус, красный, аутлайн,
  обязательно визуально отличим от "Завершён" (это не одно и то же:
  завершён = успешно закрыт, отменён = не состоялся).

Задай единую систему: один набор акцентных цветов, одна библиотека
чипов/бейджей статусов, одна карточка товара, один стиль кнопок — и
переиспользуй её во всех последующих экранах, даже если я прошу их по
одному в разных сообщениях. Если нужно — в первом же артефакте сделай
маленький "лист стилей" (палитра + кнопка + чип + карточка), чтобы я
мог на него ссылаться в следующих промптах.

Если хочешь — можешь опираться на файл `DesignTools/DESIGN.md` в этом
репозитории, там те же цвета/шрифты/компоненты уже сведены в единый
токен-набор (можешь вставить его текстом в этот же системный контекст,
если так удобнее).

Пиши интерфейс на русском языке (это соответствует языку группы, где
используется бот). Используй HTML+CSS(+немного JS для интерактивности:
степперы, переключение табов, раскрытие сверки) в одном Artifact на
экран.
```

## Промпты по экранам

Вставляй по одному, в этом порядке (порядок соответствует пути обычного
участника, потом — админа).

### 1. Дизайн-система (сделать первым)

```
Прежде чем рисовать конкретные экраны — собери маленькую страницу
"дизайн-система" на тёмном фоне: палитра цветов (фон, поверхность
карточки, приподнятая поверхность, текст основной/вторичный, акцент,
4 статус-бейджа — 2 заливкой, 2 аутлайном, из системного контекста),
кнопка (основная-заливка + вторичная-на-поверхности + деструктивная-
аутлайн-красная), карточка позиции товара (бренд, вкус, граммовка,
цена, степпер количества — суммы и цифры моноширинным шрифтом), поле
ввода, пример таб-бара снизу (2-4 текстовые вкладки, активная
подчёркнута акцентом), пустое состояние списка. Всё на одной странице,
подписано. Дальше я буду просить экраны "в этом же стиле".
```

### 2. Список активных заказов (экран участника)

```
В стиле дизайн-системы выше сделай экран "Активные заказы" для
участника группы. Это то, что видит юзер по команде /orders или из
меню — список заказов в статусах "Сбор заказов" и "На сверке",
сгруппированных по продавцу (карточка на заказ: название барыги,
статус-бейдж, число позиций пользователя в этом заказе и его сумма в
€, если уже что-то добавил, иначе "Ты ещё не заказывал"). Тап по
карточке — переход внутрь заказа. Наверху — заголовок и, если заказов
нет, пустое состояние с понятным текстом. Ничего для админа тут не
добавляй, это экран рядового участника.
```

### 3. Экран заказа — статус "Сбор заказов" (добавление позиций)

```
В том же стиле — главный экран заказа для участника, статус "Сбор
заказов". Сверху — название барыги + статус-бейдж. Список ассортимента
сгруппирован по бренду, внутри бренда — доступные вкусы, для каждого
вкуса — доступные граммовки как переключаемые чипы (100г/250г) и
степпер количества (+/-, значение, отключена кнопка "-" на нуле).
Ниже — плавающая панель/MainButton с текущей сводкой пользователя: "Твой
заказ: N позиций, X.XX кг, Y.YY €" и кнопкой перехода к своей сводке.
Учти, что у части вкусов может не быть выбранной граммовки в наличии —
такую граммовку показывай неактивной (перечёркнутый чип).
```

### 4. Экран заказа — статус "На сверке" (только чтение для участника)

```
Та же структура экрана заказа, но статус "На сверке": заголовок с
жёлтым бейджем "На сверке", под ним — заметный, но не пугающий баннер
"Добавление позиций закрыто, идёт сверка с продавцом". Список — уже не
редактируемый: показываем свои позиции как обычный список (без
степперов, без чипов-переключателей), с итоговой суммой внизу. Если
админ докинул участнику позицию вручную — такая строка помечена мелкой
подписью "добавлено администратором".
```

### 5. Своя сводка по заказу (участник)

```
Экран "Мой заказ" — детальная сводка по одному заказу для участника:
список своих позиций (бренд, вкус, граммовка, кол-во, сумма строки),
итоговая строка (кг и €), блок статуса оплаты — бейдж "Оплачено" /
"Не оплачено" (участник его не меняет, только видит, отметку ставит
админ). Внизу — статус самого заказа (переиспользуй чип).
```

### 6. Экран истории заказов (участник)

```
Список завершённых и отменённых заказов участника — те же карточки, что
в "Активных заказах", но с аутлайн-бейджем ("Завершён" серый / "Отменён"
красный, оба без заливки — это архивные статусы) и без действия
"перейти добавлять", только "посмотреть детали" (та же сводка, что в
экране 5, но полностью read-only и без блока оплаты как активного
действия — просто факт).
```

### 7. Админ — старт нового заказа

```
Экран/модалка выбора барыги для нового заказа: список продавцов, у
каждого — либо кнопка "Начать заказ", либо, если у продавца уже есть
активный заказ, задизейбленное состояние с подписью "уже есть активный
заказ" и статус-бейджем этого заказа. Это тот механизм, который не даёт
запустить два параллельных заказа у одной барыги одновременно.
```

### 8. Админ — сводный экран заказа + управление статусом

```
Расширенная версия экрана заказа для админа: тот же список позиций, но
агрегированный по всем участникам (группировка по бренду/вкусу/
граммовке с суммарным количеством, разворачивается до "кто именно
заказал" по тапу). Сверху — статус-бейдж и панель действий,
завязанная на текущий статус:
— в "Сбор заказов": кнопки "На сверку" и "Отменить заказ";
— в "На сверке": кнопки "Чек-лист сверки", "Вернуть в работу",
  "Завершить заказ", "Отменить заказ" (сделай "Завершить" акцентной
  основной кнопкой, "Отменить" — деструктивным стилем, "Вернуть в
  работу" — вторичной кнопкой).
Отдельно покажи компактный блок "слепок для барыги" — моноширинный
текстовый блок на фоне темнее самой карточки, с тонкой рамкой, похожий
на техническую распечатку, с двумя кнопками "Скопировать текст" и
"Выгрузить файл".
```

### 9. Админ — добавление позиции за участника (только в "На сверке")

```
Модалка/шторка "Добавить позицию участнику" — выбор участника из списка
(поиск по имени), затем тот же выбор бренд → вкус → граммовка →
количество, что и в обычном экране заказа, кнопка "Добавить". Подпиши
мелким текстом, что это действие доступно только в статусе "На
сверке" и что позиция будет помечена как добавленная администратором.
```

### 10. Чек-лист сверки поставки

```
Экран чек-листа: список позиций (бренд, вкус, граммовка), у каждой —
"нужно N" и счётчик "привезли M" со степпером +/-. Если M меньше N —
подсветить лёгким предупреждающим цветом (не ошибкой, просто
акцентом), если M больше N — другим акцентом (это нормальная ситуация,
не ошибка). Наверху — прогресс "сверено X из Y позиций" (позиция
считается сверенной, если по ней хоть раз нажали +/-, а не только если
M == N).
```

### 11. Оплата (список участников заказа)

```
Экран для админа — список участников этого заказа с их суммой к оплате
и переключателем "Оплачено/Не оплачено" (обычный тумблер или чип-кнопка
по тапу). Наверху — сводка "Оплачено X из Y участников, собрано Z €
из W €".
```

## Что делать с результатом

- Сохраняй понравившиеся артефакты (Claude позволяет открыть их как
  отдельную ссылку/скачать HTML) — так у нас останется набор
  референсов на все экраны из спеки.
- Из финальных макетов на этапе фронта переносим не HTML один в один, а
  цвета/отступы/компоненты (кнопка, чип, карточка) — макет тут нужен
  для согласования UX и стиля, а не как исходники для продакшена.
